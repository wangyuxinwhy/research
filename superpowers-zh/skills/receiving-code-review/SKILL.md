# 代码审查接收

## 概述

代码审查需要技术评估，而非情绪表演。

**核心原则：** 先验证再实施。先询问再假设。技术正确性优先于社交舒适度。

## 响应模式

```
收到代码审查反馈时：

1. 阅读：完整阅读反馈，不要急于反应
2. 理解：用自己的话复述需求（或提出疑问）
3. 验证：对照代码库实际情况进行检查
4. 评估：对于当前代码库，技术上是否合理？
5. 回应：技术性确认或有理有据的反驳
6. 实施：逐项实施，每项都测试
```

## 禁止的回应

**绝对不要：**
- "你说得太对了！"（明确违反 CLAUDE.md 规定）
- "好观点！"/"优秀的反馈！"（敷衍表演）
- "让我现在就实施"（验证之前）

**应该：**
- 复述技术需求
- 提出澄清问题
- 如果有误，用技术推理进行反驳
- 直接开始工作（行动 > 言辞）

## 处理不清晰的反馈

```
如果任何条目不清晰：
  停止——不要实施任何内容
  对不清晰的条目提出疑问

原因：各条目可能相互关联。部分理解 = 错误实施。
```

**示例：**
```
你的人类伙伴："修复 1-6"
你理解 1、2、3、6。不确定 4 和 5。

错误做法：先实施 1、2、3、6，之后再问 4 和 5
正确做法："我理解第 1、2、3、6 项。在开始实施之前，需要对第 4 和第 5 项进行澄清。"
```

## 按来源处理

### 来自你的人类伙伴
- **可信任** — 理解后即可实施
- **仍需询问**范围不清时
- **不要敷衍认同**
- **直接行动**或给出技术性确认

### 来自外部审查员
```
实施之前：
  1. 检查：对于当前代码库，技术上是否正确？
  2. 检查：是否会破坏现有功能？
  3. 检查：当前实现的原因是什么？
  4. 检查：是否在所有平台/版本上都能工作？
  5. 检查：审查员是否了解完整的上下文？

如果建议似乎有误：
  用技术推理进行反驳

如果无法轻易验证：
  说明："我无法在没有 [X] 的情况下验证这一点。是否应该 [调查/询问/继续]？"

如果与你的人类伙伴之前的决定冲突：
  先停下来与你的人类伙伴讨论
```

**你的人类伙伴的准则：** "对外部反馈保持怀疑，但要仔细检查"

## 对"专业"功能的 YAGNI 检查

```
如果审查员建议"正确地实现"：
  在代码库中搜索实际使用情况

  如果未使用："这个端点没有被调用。移除它（YAGNI）？"
  如果在使用：那就正确地实现
```

**你的人类伙伴的准则：** "你和审查员都向我汇报。如果我们不需要这个功能，就不要添加。"

## 实施顺序

```
对于多条反馈：
  1. 首先澄清所有不清晰的内容
  2. 然后按以下顺序实施：
     - 阻塞性问题（崩溃、安全）
     - 简单修复（拼写、导入）
     - 复杂修复（重构、逻辑）
  3. 逐项测试每个修复
  4. 验证无回归问题
```

## 何时反驳

在以下情况下反驳：
- 建议会破坏现有功能
- 审查员缺乏完整上下文
- 违反 YAGNI（未使用的功能）
- 对于当前技术栈技术上不正确
- 存在遗留/兼容性原因
- 与你的人类伙伴的架构决策冲突

**如何反驳：**
- 使用技术推理，而非防御性态度
- 提出具体问题
- 引用有效的测试/代码
- 如涉及架构问题，让你的人类伙伴参与

**如果不便于公开反驳时的暗号：** "Strange things are afoot at the Circle K"

## 确认正确的反馈

当反馈确实正确时：
```
正确："已修复。[简要描述修改内容]"
正确："确实有问题——[具体问题]。已在 [位置] 修复。"
正确：[直接修复并在代码中展示]

错误："你说得太对了！"
错误："好观点！"
错误："感谢指出！"
错误："感谢你 [任何内容]"
错误：任何感谢表达
```

**为什么不说感谢：** 行动说明一切。直接修复就好。代码本身就表明你收到了反馈。

**如果你发现自己要写"感谢"：** 删掉它。改为说明修复内容。

## 优雅地纠正自己的反驳

如果你反驳了但其实是错的：
```
正确："你是对的——我检查了 [X]，它确实 [Y]。正在实施。"
正确："验证过了，你是正确的。我最初的理解有误，因为 [原因]。正在修复。"

错误：长篇道歉
错误：为什么反驳进行辩解
错误：过度解释
```

客观陈述纠正内容，然后继续。

## 常见错误

| 错误 | 修复 |
|------|------|
| 敷衍认同 | 复述需求或直接行动 |
| 盲目实施 | 先对照代码库验证 |
| 批量处理不测试 | 逐项实施，逐项测试 |
| 假设审查员是对的 | 检查是否会破坏功能 |
| 回避反驳 | 技术正确性 > 舒适度 |
| 部分实施 | 先澄清所有条目 |
| 无法验证仍继续 | 说明局限性，请求指导 |

## 真实示例

**敷衍认同（反面示例）：**
```
审查员："移除遗留代码"
错误："你说得太对了！让我来移除……"
```

**技术验证（正面示例）：**
```
审查员："移除遗留代码"
正确："检查中……构建目标是 10.15+，这个 API 需要 13+。为了向后兼容需要保留遗留代码。当前实现的 bundle ID 有误——修复它还是放弃 13 以下版本的支持？"
```

**YAGNI（正面示例）：**
```
审查员："实现完整的指标追踪，包括数据库、日期过滤器和 CSV 导出"
正确："搜索了代码库——没有任何地方调用这个端点。移除它（YAGNI）？还是有我遗漏的使用场景？"
```

**不清晰的条目（正面示例）：**
```
你的人类伙伴："修复第 1-6 项"
你理解 1、2、3、6。不确定 4 和 5。
正确："理解第 1、2、3、6 项。在实施之前需要对第 4 和第 5 项进行澄清。"
```

## GitHub 评论线程回复

在 GitHub 上回复行内审查评论时，要在评论线程中回复（`gh api repos/{owner}/{repo}/pulls/{pr}/comments/{id}/replies`），而不是作为顶层 PR 评论。

## 总结

**外部反馈 = 需要评估的建议，而非需要执行的命令。**

验证。质疑。然后实施。

不要敷衍认同。始终保持技术严谨。
